# Storage and website pipeline

Status: **Prompt 5 source implemented; no live R2/E2B/Vercel operation, generated-source sandbox execution or deployment has been performed**.

## Cloudflare R2

The S3-compatible client uses endpoint `https://<account>.r2.cloudflarestorage.com`, region `auto` and server-only access credentials. Object keys are generated by the server as `users/{userId}/{kind}/{opaqueAssetId}.{safeExtension}`. Browser-selected key/bucket paths are not accepted; ownership checks reject mismatched prefixes, `..`, backslashes and excessive key lengths. Content hashes are stored/verified as metadata rather than used as the key.

`PutObjectCommand` stores generated bytes with explicit content type, length, SHA-256 checksum and safe owner/job metadata. Keys use a fresh opaque asset ID; the code does not claim deterministic conditional-create retry semantics. R2 cannot participate in the PostgreSQL transaction, so an upload followed by database failure can orphan an object and requires operational reconciliation.

The implemented download boundary issues a five-minute `GetObjectCommand` signed URL only after owner/state/key checks; responses do not expose credentials or unrestricted keys. Server-owned reads use early length checks, bounded streams and checksum verification. No public direct-upload/signing route is implemented in this revision, so malware/content scanning and a future untrusted-upload policy remain separate launch work.

## Generated source validation

Website source is limited to a fixed static application recipe: bounded `index.html`, `styles.css` and `script.js` (plus explicitly allowed local assets if later supported). The server supplies the manifest; model output cannot add packages, install scripts, environment variables, build commands or external configuration.

Validation rejects absolute/parent paths, duplicates, symlinks, oversized files/source, executable HTML injected into Orindle, remote script origins not on the allowlist, and JavaScript syntax errors. Network-facing URLs and dependencies are reviewed for SSRF and supply-chain risk. Source is stored privately and is never returned in admin DTOs.

## E2B isolation

The official `e2b` SDK uses `Sandbox.create()`, `sandbox.files.write()` and `sandbox.commands.run()`. Only validated source and a fixed command are sent. No production credentials or privileged environment variables are inherited. Sandboxes have timeouts, limited file/command budgets and are killed in `finally`. Network access is disabled unless the fixed recipe demonstrably requires it; this implementation's static recipe needs no install/network step.

The application server never runs generated JavaScript, `npm install`, generated shell, dynamic import or `eval`. Build output/logs are truncated and mapped to safe error codes before storage or display.

## Scoped Vercel deployment

Only a source version with a successful E2B validation record is eligible. The server calls the documented `POST https://api.vercel.com/v13/deployments` with a scoped bearer token, configured `teamId`, server-generated project name, inline small files and `target: "preview"` by default. No generated environment variables, Git credentials, arbitrary project ID, alias, team or production target are accepted from the customer.

The persisted deployment ID is restricted; the customer receives only a validated HTTPS deployment URL and safe state. Status polling is read-only and idempotent. Production target/custom domains require a separate explicit server allowlist and authorized operational policy. This task does not perform a live deployment.

## Failure handling

Storage/deployment retries never regenerate source. If Vercel acceptance is unknown after a timeout, the current code marks the create uncertain and blocks another automatic create when no provider deployment ID is stored; an operator must reconcile provider/team/project evidence before retry. A deployment URL is shown only after provider confirmation. Failed validation blocks publish and leaves prior valid versions unchanged.
