# Architecture

## Stage boundary

Prompt 1 is a static-friendly Next.js App Router frontend. Public pages are Server Components by default. Client Components are limited to navigation, accessible accordions, the contact preview and sparse motion. Content and pricing live in typed local modules; there are no database writes or real transactions.

## Implemented boundaries

```text
app/                         routes, metadata, fonts, icon, OG image, sitemap, robots
components/
  layout/                    shared header, footer, mobile/products navigation, containers, logo
  ui/                        shadcn-compatible button and accordion primitives
  marketing/                 editorial sections, product visuals, pricing, FAQ, contact/auth previews
  blog/                      article body, rich-text links and cards
  seo/                       safe JSON-LD script component
lib/
  content/                   typed products, models, pricing, FAQs and six article modules
  contracts/                 frontend-only contact/checkout interfaces
  mocks/                     explicitly non-delivering local contact adapter
  site.ts                    canonical origin and metadata helpers
  utils.ts                   class-name, number and formatting utilities
tests/                       Vitest unit/component suites and Playwright production checks
docs/                        living project record and staged handoffs
```

There is no runtime `public/` asset dependency: the original mark is inline SVG, the icon is an App Router file convention, fonts are local to `app/fonts`, and the social image is generated by `app/opengraph-image.tsx`.

## Prompt 2 authentication frontend architecture

Prompt 2 adds a parallel `components/auth/` UI layer and `lib/auth/` validation/presentation helpers. Existing marketing routes remain server-first. Auth pages are Server Components that await allowlisted `searchParams`; only forms, password visibility and OAuth preview buttons are Client Components. The shared `AuthShell` is server-rendered and uses the existing public header/footer and tokens.

`lib/contracts/authentication.ts` defines provider-neutral operations for signup, login, logout, password reset/update, email verification/resend, OAuth start/callback, session snapshots and route access. `lib/mocks/authentication-preview.ts` is the only Prompt 2 adapter and returns explicit preview/unavailable results with no user, session, redirect or provider payload. It performs no network, cookie, storage or email operation.

The callback remains an `app/auth/callback/page.tsx` presentation placeholder. Prompt 5 must replace it with the current researched server Route Handler and Supabase SSR cookie/code exchange; do not add a conflicting route by assumption. All auth pages are noindex and excluded from the sitemap. Presentation-state query values are allowlisted; auth codes, tokens and arbitrary `next` URLs are ignored.

See `authentication-design.md` for component responsibilities and `authentication-flows.md` for route/state transitions.

## Dependency direction

Routes compose content and components. Content modules do not import React or route code. UI primitives have no product/business rules. Pricing displayed on the public site is presentational typed content; later server configuration becomes authoritative and must be reconciled before checkout. SEO helpers receive explicit canonical paths and never infer request hosts from untrusted headers. JSON-LD is serialized by a small component that escapes `<` to reduce script-breakout risk.

`components/ui/button.tsx` has an explicit client boundary because the installed Radix Slot uses client context during module evaluation. This does not make the whole marketing site a Client Component; Server Components can still compose the button around native links.

## Rendering and SEO

Long-form articles are server-rendered from structured local content so headings, links and body copy are crawlable without client JavaScript. Dynamic article slugs use `generateStaticParams`, `generateMetadata` and a not-found boundary. Four product pages are statically parameterized. `/signup` is dynamic because it awaits a display-safe pack query parameter. Sitemap content includes only indexable public routes and articles; login/signup previews are noindex and excluded.

## Interaction and motion

Native links provide real navigation. The Products menu and mobile dialog use Radix primitives; the mobile dialog supports Escape and focus return. FAQ accordions expose `aria-expanded`. Contact validation is local and returns an explicit preview result. Motion reveals use `initial={false}`, so content is visible by default; permitted motion is a small transform keyframe and reduced motion removes it.

## Future backend contract

Later stages add server-only repositories and service adapters for identity, entitlements, wallet ledger, assets, projects and usage. Browser code submits intent and receives display-safe results. It never supplies authoritative credit price, provider cost or deduction amount. Payment webhooks and AI metering remain server-only and idempotent.

## Data and state

There is no global client state requirement in Prompt 1. Interactive UI owns local state. The mock contact adapter returns an explicit preview state rather than claiming persistence. `CheckoutService` is only an interface for later integration; no checkout adapter is called by the current signup preview.

## Environments

Local development and preview use the same static content. `NEXT_PUBLIC_SITE_URL` controls canonical absolute URLs and falls back to the documented provisional origin. Optional `NEXT_PUBLIC_CONTACT_EMAIL` is used only if a verified inbox is configured. Secrets are neither required nor accepted by the public frontend.
