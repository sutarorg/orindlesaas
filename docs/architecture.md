# Architecture

## Stage boundary

Prompt 5 implements the server modular-monolith contract in `backend-architecture.md`; local evidence and unexecuted live gates are tracked in `progress.md` and `handoff-prompt6.md`. The inherited Prompt 1–4 sections below are stage history, not a description of current demo behavior.

Current server boundaries include `app/api/` versioned handlers and signed callbacks, `proxy.ts` plus `lib/supabase/` for SSR cookie handling, `lib/server/auth/` for verified active-profile/permission/recent-AAL2 guards, `lib/server/db/` for Drizzle schema/access, and domain modules for credits, payments, AI, chat, generations, jobs, storage, websites, email, workspace and admin. `components/dashboard/` and `components/admin/` consume owner/permission-scoped server results rather than routed fixture adapters. See `api-reference.md` for the actual implemented endpoint inventory.

Prompt 1 was a static-friendly Next.js App Router frontend. Public pages are Server Components by default. Client Components are limited to navigation, accessible accordions, the contact preview and sparse motion. Content and pricing live in typed local modules; there are no database writes or real transactions.

## Prompt 2 authentication frontend architecture

Prompt 2 adds a parallel `components/auth/` UI layer and `lib/auth/` validation/presentation helpers. Existing marketing routes remain server-first. Auth pages are Server Components that await allowlisted `searchParams`; only forms, password visibility and OAuth preview buttons are Client Components. The shared `AuthShell` is server-rendered and uses the existing public header/footer and tokens.

`lib/contracts/authentication.ts` defines provider-neutral operations for signup, login, logout, password reset/update, email verification/resend, OAuth start/callback, session snapshots and route access. `lib/mocks/authentication-preview.ts` is the only Prompt 2 adapter and returns explicit preview/unavailable results with no user, session, redirect or provider payload. It performs no network, cookie, storage or email operation.

The callback remains an `app/auth/callback/page.tsx` presentation placeholder. Prompt 5 must replace it with the current researched server Route Handler and Supabase SSR cookie/code exchange; do not add a conflicting route by assumption. All auth pages are noindex and excluded from the sitemap. Presentation-state query values are allowlisted; auth codes, tokens and arbitrary `next` URLs are ignored.

See `authentication-design.md` for component responsibilities and `authentication-flows.md` for route/state transitions.

## Prompt 3 dashboard frontend architecture

The customer workspace uses `/app` and a nested `app/app/layout.tsx` with a unified DashboardShell. Existing public/auth routes move under URL-neutral `app/(site)/`; its nested layout owns SiteHeader/SiteFooter/public JSON-LD while the root layout retains only shared metadata/fonts/body. This prevents marketing chrome from entering the application without changing public URLs.

`components/dashboard/` contains task-specific client islands and shared shell/model/message primitives. `lib/contracts/dashboard.ts` defines display-safe workspace, generation, project, asset, wallet, settings and website operations. `lib/dashboard/` owns typed fixtures, documented model registry, navigation and deterministic fixture estimates. `lib/mocks/dashboard-preview.ts` is the only mutation adapter and returns non-persistent preview results with zero credits changed.

Server pages compose fixture content. Local filters, dialogs, editors, clipboard, attachment-name selection and preview state are Client Components. Dynamic conversation/website pages await `params`, look up allowlisted fixture IDs and call not-found for unknown values. No AI SDK, Monaco, charting or backend package is introduced.

All `/app` routes inherit noindex and are excluded from the sitemap/robots-allowed area. The visible demo workspace is not authenticated or authorized. See `dashboard-architecture.md` for component/trust boundaries and `dashboard-navigation.md` for the complete route map.

## Prompt 4 administration frontend architecture

Prompt 4 adds an independent noindex `/admin` nested shell with 13 operations routes, grouped navigation, global local-fixture search, notifications, demo profile and breadcrumbs. Public/auth and customer shells remain isolated. An admin catch-all supplies safe unknown-route UI without a parent loading boundary that could obscure 404 statuses.

`components/admin/` contains data-oriented shell/table/chart/dialog primitives and feature workspaces. `lib/contracts/admin.ts` defines display-safe operational DTOs, proposed permissions and mutation-like intents. `lib/admin/` owns deterministic fictional fixtures, navigation, UTC/minor-unit formatting and documented metric calculations. `lib/mocks/admin-preview.ts` is the only admin mutation adapter and returns non-persistent results with zero credits/payment changes and no persisted audit.

Native tables, responsive named scroll regions and local filter/pagination are preferred to an incomplete ARIA grid. Lightweight SVG/HTML charts include text and tabular equivalents. No table/chart/RBAC/database/provider package is introduced. Real admin identity, authorization, queries, health checks, financial/credit operations and audit persistence remain Prompt 5 work. See `admin-architecture.md`, `admin-permissions.md` and `admin-data-contracts.md`.

## Dependency direction

Routes compose content and components. Content modules do not import React or route code. UI primitives have no product/business rules. Pricing displayed on the public site is typed content; checkout now locks and reconciles the exact enabled database/server pack before creating a purchase, so browser values are never authoritative. SEO helpers receive explicit canonical paths and never infer request hosts from untrusted headers. JSON-LD is serialized by a small component that escapes `<` to reduce script-breakout risk.

`components/ui/button.tsx` has an explicit client boundary because the installed Radix Slot uses client context during module evaluation. This does not make the whole marketing site a Client Component; Server Components can still compose the button around native links.

## Rendering and SEO

Long-form articles are server-rendered from structured local content so headings, links and body copy are crawlable without client JavaScript. Dynamic article slugs use `generateStaticParams`, `generateMetadata` and a not-found boundary. Four product pages are statically parameterized. `/signup` is dynamic because it awaits a display-safe pack query parameter. Sitemap content includes only indexable public routes and articles; login/signup previews are noindex and excluded.

## Interaction and motion

Native links provide real navigation. The Products menu and mobile dialog use Radix primitives; the mobile dialog supports Escape and focus return. FAQ accordions expose `aria-expanded`. Contact validation is local and returns an explicit preview result. Motion reveals use `initial={false}`, so content is visible by default; permitted motion is a small transform keyframe and reduced motion removes it.

## Backend trust contract

Server-only repositories and service adapters own identity, entitlements, wallet ledger, assets, projects and usage. Browser code submits intent and receives display-safe results. It never supplies authoritative credit price, provider cost or deduction amount. Payment webhooks and AI metering remain server-only and idempotent; live verification is still required as recorded in `handoff-prompt6.md`.

## Prompt 1 data and state history

There was no global client state requirement in Prompt 1. Interactive UI owns local state. The mock contact adapter returns an explicit preview state rather than claiming persistence. `CheckoutService` is only an interface for later integration; no checkout adapter is called by the current signup preview.

## Environments

Local development and preview use the same static public content. `NEXT_PUBLIC_SITE_URL` controls canonical absolute URLs and falls back to the documented provisional origin. Optional `NEXT_PUBLIC_CONTACT_EMAIL` is used only if a verified inbox is configured. Public browser configuration contains no secrets; real backend operations separately require authorized server-only credentials and fail closed when absent.
